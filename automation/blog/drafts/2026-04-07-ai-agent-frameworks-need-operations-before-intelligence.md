최근 GeekNews에서 OpenClaw를 소개한 글을 다시 보다가, AI 에이전트 프레임워크를 설명할 때 자주 빠지는 지점이 또렷하게 보였다. 많은 글이 에이전트를 설명할 때 아래 요소에 집중한다.

- 어떤 모델을 붙였는가
- 프롬프트 체인이 얼마나 똑똑한가
- 웹 브라우징이나 코드 실행을 할 수 있는가
- 자율적으로 여러 단계를 수행하는가

물론 이런 요소도 중요하다. 처음 데모를 볼 때 가장 눈에 띄는 것도 대개 이런 부분이다. 하지만 실제로 며칠, 몇 주, 몇 달 동안 돌아가는 시스템을 만들려면 질문이 달라진다.

**이 에이전트는 실패했을 때 어떻게 복구되고, 누가 통제하고, 어떤 기록이 남고, 어디까지 믿어도 되는가?**

내 기준에서는 AI 에이전트 프레임워크의 완성도를 볼 때 모델 지능보다 먼저 봐야 하는 것이 있다. 바로 **운영 계층(operations layer)** 이다.

## 왜 데모에서는 지능이 먼저 보이고, 실전에서는 운영이 먼저 문제 되나

데모 환경에서는 대부분 조건이 좋다.

- 단일 사용자다
- 짧은 작업만 수행한다
- 실패하면 그냥 다시 실행하면 된다
- 외부 시스템 영향이 작다
- 로그를 사람이 눈으로 따라갈 수 있다

이 환경에서는 당연히 모델 성능과 도구 호출 성공률이 가장 중요해 보인다. 하지만 운영 환경으로 넘어가면 상황이 바뀐다.

- 에이전트가 여러 채널에서 동시에 요청을 받는다
- 장시간 살아 있어야 한다
- 작업 상태를 이어 받아야 한다
- 권한이 다른 도구들을 함께 다뤄야 한다
- 실패가 외부 서비스나 실제 계정에 영향을 준다

이 순간부터 문제는 “얼마나 똑똑한가”보다 “얼마나 통제 가능한가”로 옮겨간다.

## 실제로 먼저 필요한 것은 다섯 가지다

내가 보기엔 에이전트 프레임워크가 실무에서 버티려면 최소한 아래 다섯 가지가 먼저 필요하다.

### 1. 스케줄링

에이전트는 한 번 잘 대답하는 챗봇과 다르다. 반복 작업, 지연 실행, 정기 점검, 백그라운드 작업을 처리해야 한다.

예를 들면 이런 식이다.

- 아침마다 특정 소스 확인
- 몇 시간 간격으로 서비스 상태 점검
- 작업이 오래 걸리면 백그라운드로 넘기기
- 특정 이벤트 이후 재시도 예약

스케줄링이 없으면 에이전트는 결국 “대화창 안에서만 움직이는 도구”에 머문다. 반대로 스케줄링이 있으면 비로소 운영 주체처럼 행동할 수 있다.

### 2. 영구 상태와 세션 관리

에이전트는 매번 처음부터 시작하면 금방 비효율이 커진다. 작업 중간 상태, 최근 결정, 세션 문맥, 보류 중인 실행이 남아 있어야 한다.

이게 없으면 아래 문제가 반복된다.

- 방금 하던 작업을 다시 설명해야 한다
- 길게 진행되는 수정 작업이 끊긴다
- 복수의 작업이 섞였을 때 분리가 안 된다
- 실패 후 어디까지 진행됐는지 알 수 없다

즉, “똑똑한 응답”보다 먼저 **일의 맥락을 유지하는 구조**가 필요하다.

### 3. 로그와 추적 가능성

실전에서는 성공보다 실패 분석이 더 중요할 때가 많다. 그런데 많은 에이전트 데모는 결과만 보여주고, 중간 과정은 희미하다.

운영에서는 최소한 이 정도는 남아야 한다.

- 어떤 요청이 들어왔는가
- 어떤 도구를 호출했는가
- 어떤 세션이나 서브에이전트가 처리했는가
- 실패 지점이 어디인가
- 재시도나 롤백이 일어났는가

로그가 없으면 시스템이 좋아졌는지 나빠졌는지도 판단하기 어렵다. 한두 번 운 좋게 통과한 데모와, 반복 가능한 운영 시스템의 차이는 여기서 크게 벌어진다.

### 4. 권한 경계

AI 에이전트는 브라우저, 셸, 메시징, 파일 시스템, 외부 API를 한데 묶는 경우가 많다. 이때 가장 무서운 건 능력이 아니라 **경계 없는 능력**이다.

예를 들어 아래 차이는 매우 크다.

- 읽기만 가능한 파일 접근
- 특정 디렉터리만 수정 가능한 쓰기 권한
- 승인 후에만 가능한 고위험 명령 실행
- 외부 메시징은 별도 도구를 통해서만 허용

운영 계층이 약한 시스템은 결국 “할 수 있는 것”만 늘어난다. 운영 계층이 강한 시스템은 “어디까지, 어떤 조건에서 하게 할 것인가”를 함께 설계한다.

### 5. 복구와 롤백

에이전트는 실수한다. 이건 모델이 아무리 좋아져도 사라지지 않는다. 그래서 중요한 건 실수를 막는 능력만이 아니라, **실수 후 되돌아오는 능력**이다.

예를 들면 아래가 필요하다.

- 실패한 작업을 재개할 수 있는가
- 이전 상태로 롤백할 수 있는가
- 자동 재시도가 안전한가
- 사람에게 개입 요청을 보낼 수 있는가

복구 경로가 없는 자동화는 한 번 멋져 보여도 오래 못 간다.

## 운영 계층이 약하면 생기는 전형적인 문제

이건 특정 프레임워크 하나의 문제가 아니라, 많은 AI 에이전트 프로젝트에서 공통으로 보이는 패턴이다.

### 문제 1. 잘 되다가 어느 순간 멈춘다

처음엔 잘 되는 것처럼 보인다. 그런데 며칠 지나면 아래 같은 일이 생긴다.

- 백그라운드 작업이 조용히 죽는다
- 외부 API 제한에 걸린 뒤 회복하지 못한다
- 메시지 라우팅이 꼬여서 응답이 사라진다
- 세션 상태가 어긋나서 다음 작업이 이상해진다

이건 대개 모델 지능 문제가 아니다. 운영 신호가 약해서 생기는 문제다.

### 문제 2. 실패 원인을 설명할 수 없다

결과가 이상한데 이유를 모른다. 어떤 프롬프트가 문제였는지, 어떤 도구가 실패했는지, 사람이 승인했는지, 자동 재시도가 있었는지조차 흐리다.

이 상태가 되면 시스템은 똑똑한 게 아니라 **우연히 굴러가는 박스**가 된다.

### 문제 3. 권한이 넓은데 책임 경로가 없다

에이전트가 파일 수정도 하고, 브라우저 클릭도 하고, 메시지 전송도 하고, 외부 계정도 건드리는데, 어느 행동이 어떤 규칙으로 허용됐는지 알 수 없다면 위험하다.

이 경우는 성능보다 신뢰 문제가 먼저 터진다.

## OpenClaw 같은 구조가 흥미로운 이유

GeekNews에서 OpenClaw를 설명한 글이 흥미로운 이유도 여기에 있다. 단순히 LLM을 감싼 래퍼라기보다, 에이전트를 오래 굴리기 위한 운영 요소들을 전면에 두려는 시도가 보이기 때문이다.

예를 들면 이런 관점이다.

- 여러 채널을 통한 메시징
- 세션과 서브에이전트 관리
- 도구 권한 분리
- 로그와 상태 확인
- 백그라운드 작업 및 하트비트

이런 구조는 화려한 데모보다 덜 눈에 띌 수 있다. 하지만 실제로는 이런 층이 있어야 에이전트가 “한 번 신기한 것”에서 “지속적으로 쓸 수 있는 것”으로 넘어간다.

## 내가 보는 현실적인 우선순위

AI 에이전트 프레임워크를 고를 때나 만들 때, 나는 아래 순서로 본다.

### 1. 모델 성능보다 실패 처리 경로가 있는가

좋은 모델은 중요하다. 하지만 실패했을 때 사람에게 어떻게 돌아오는지, 어떤 로그를 남기는지, 어디서 재개하는지가 더 먼저다.

### 2. 도구 수보다 권한 구조가 선명한가

도구가 많다고 좋은 게 아니다. 오히려 많을수록 경계가 분명해야 한다.

### 3. 자율성보다 운영 가시성이 있는가

“알아서 한다”는 말은 듣기 좋다. 그런데 실전에서는 “알아서 한 과정을 내가 볼 수 있는가”가 더 중요하다.

### 4. 자동화 범위보다 롤백 가능성이 있는가

넓게 자동화하는 것보다, 제한된 범위에서 안전하게 되돌릴 수 있는 시스템이 더 오래 살아남는다.

## 간단한 체크리스트

새로운 AI 에이전트 프레임워크를 볼 때 나는 대략 이런 질문을 던진다.

- 작업 스케줄링이 되는가?
- 장시간 세션과 상태를 유지하는가?
- 도구 호출과 실패 로그를 추적할 수 있는가?
- 권한이 구획되어 있는가?
- 롤백이나 사람 개입 경로가 있는가?
- 멀티채널이나 장기 운영을 전제로 설계됐는가?

이 질문에 답이 약하면, 그 시스템은 지능형 데모일 수는 있어도 운영 가능한 에이전트라고 부르긴 어렵다.

## 결론

AI 에이전트 분야에서는 늘 모델이 가장 화려하게 보인다. 하지만 실전에서는 지능보다 운영이 더 빨리 바닥을 드러낸다.

- 스케줄링이 없으면 반복 작업이 불안정하고
- 상태 관리가 없으면 긴 작업이 끊기고
- 로그가 없으면 실패를 분석할 수 없고
- 권한 경계가 없으면 위험이 커지고
- 롤백이 없으면 실수를 감당할 수 없다

그래서 나는 AI 에이전트 프레임워크를 볼 때 먼저 이렇게 묻는 편이다.

**이 시스템은 얼마나 똑똑한가?** 보다 먼저,
**이 시스템은 얼마나 오래, 안전하게, 설명 가능하게 굴릴 수 있는가?**

실무에서 살아남는 건 대개 더 화려한 지능이 아니라, 더 단단한 운영 구조다.
